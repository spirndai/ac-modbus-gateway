# 核心原理

## 1. 问题与思路

约克水系统中央空调（实测面板型号 MC2100，带 RS485 接口）的主机与各面板之间通过 RS485 总线以 Modbus RTU 协议通信。厂家不提供公开的远程控制接口，但这条总线对用户是可见的——我们选择**在总线上做文章**，而不是拆机、换面板或依赖不存在的云 API。

整体思路分两步：

1. **监听**：把网关并联在总线上（只读），把主机与面板之间的全部问答数据原样转发到服务器解析——空调的每一个状态（开关、模式、温度、风速、水泵）都能从总线上读到
2. **控制**：服务器需要下发命令时，把一帧标准的 Modbus 写命令交给网关，网关在**总线空闲时**将其注入总线，直接写对应面板的寄存器——面板不区分命令来源，收到合法的写命令即执行动作

难点全部在第 2 步：网关相当于在一条已有主站的 RS485 总线上"额外"说话，如何保证不干扰原通信？答案来自对总线时序的实测观察。

### 控制为什么可行

系统的正常流程是：**人操作面板 → 面板调整自身状态 → 主机下次轮询时读到新设置**。主机在这条总线上只做"读"，面板负责应答。

控制之所以可行，根本上是因为 **Modbus RTU 协议本身没有来源校验的概念**——帧里只有从站地址、功能码、数据和 CRC，不存在任何"发送者身份"信息。从站只判断帧的地址是否指向自己、CRC 是否正确，不会（也无法）判断命令来自主机还是总线上其他节点。总线上任何节点发出的合法写命令（功能码 0x06），面板都会执行。

实测验证：模拟主机向面板下发写命令，面板正常执行动作。于是控制路径完全复用总线既有机制：

```
网关(写命令) ──► 面板执行动作 ──下次轮询──► 主机读到新状态
```

对面板而言，这与"有人在面板上操作了一下"没有区别；对主机而言，这只是某台面板的设置变为了新值。整个系统保持自洽，不需要任何一方"知道"网关的存在。

另一个佐证来自约克系统本身的设计：**面板本来就是"会接收命令"的设备**。以模式为例，1 号面板是主控面板——1 号设为制暖，全系统都变制暖；1 号设为制冷，全系统都变制冷；若有面板模式与 1 号不一致，**主机会主动向该面板下发命令**把它改回来。也就是说，"主机向面板写命令"本就是这套系统的正常运行方式，网关的注入只是走了同一条既定路径。

## 2. 总线时序分析（关键）

### 观察到的总线行为

主机作为主站，按顺序轮询各个面板（每个面板有独立地址，见部署指南"面板地址"），总线上出现规律性的问答帧：

```
        一次"问答"
        ├──────────┤
   ┌────┐        ┌──────────────┐        ┌────┐
   │请求│ ~10ms  │    响应      │ ~100ms │请求│  ...
   └────┘        └──────────────┘        └────┘
  8字节          69字节                  下一个面板
```

实测时序（9600 8N1，1 字节 = 10 bit ≈ 1.04ms）：

| 间隔 | 实测值 | 说明 |
|---|---|---|
| 请求 → 响应 | ~10ms | 面板的应答延迟 |
| 响应 → 下一次请求 | **~100ms** | 主机收到应答后的总线空闲 |
| 一帧命令（8 字节）传输时长 | ~8.4ms | 注入一帧命令所需的最短时间 |

### 注入窗口推导

- 总线空闲超过 **20ms** 时，说明当前轮询已完成、下一次轮询至少还有 ~80ms 才开始
- 一帧命令只需 ~8.4ms 即可传输完毕
- 因此：**空闲 > 20ms 时注入一帧命令，总线来得及回到空闲状态迎接下一次轮询，不会与主站冲突**

这是整个方案成立的核心结论——网关的"发言纪律"由总线自身的节奏决定，而不是靠猜测。

### 固件中的注入状态机

```
loop():
    串口有数据吗？
    ├─ 有 → 总线忙碌（bus_idle = false），累计数据
    └─ 无 → 总线刚变为空闲？记录空闲起点 last_free_time
             │
             ├─ 空闲 ≥ 20ms：依次执行（每次只做一件）
             │    1. 有待发命令 → CRC 校验通过后写入总线
             │    2. 有累计的总线数据 → UDP 上报服务器
             │    3. 都没有 → 处理 OTA
```

命令的优先保证：

1. 命令帧写入前必须通过 **CRC-16 校验**，脏数据绝不进总线
2. 写命令与上报数据不会同时进行，避免缓冲区竞争
3. 服务器侧命令之间强制间隔 **≥5 秒**，给总线充分的恢复时间（`websvr/utils.py` 中的 `send_udp_packet`）

## 3. 系统数据流设计

### 为什么固件只"搬运"，解析放在服务器

- 固件改动成本高：网关装在总线附近，重烧固件需要现场操作（保留 OTA 作为兜底）
- 协议解析规则可能需要按机型调整：放在服务器端改 Python 即可
- 固件越简单越可靠：ESP32 只做三件事——监听、转发、空闲注入

### 服务器端的流量处理

总线上的数据重复率极高（主机每秒都在轮询，状态却很少变化）。服务器端做两级去重：

1. **内存级**：同一设备连续的相同寄存器值直接跳过，不产生数据库写入（`svr.py` 的 `last_state`）
2. **数据库级**：完全相同的报文只存一行（`modbusmsg` + JSONB hash 索引），每次出现只追加一行时间记录（`modbustime`）——既省空间又天然形成"状态变化时间线"

### 设备识别与寻址

485 总线是**整个系统连通**的：所有面板与主机挂在同一条总线上，所以**一条总线只需要一个 ESP32 网关**——装在任意一个面板处，就能听到所有面板的问答数据，也能向任意面板注入命令。

- **面板身份**：来自 Modbus 帧里的从站地址（工程模式设置），服务器据此知道状态属于哪个房间
- **网关地址**：UDP 数据包的源 IP。服务器把它记录进 `modbusclient` 表，下发命令时按面板查表、发回网关。DHCP 换了 IP 也无需配置，下次上报自动更新

> 个别部署环境（部分 NAS/Docker 的 UDP 端口映射实现）会把容器内看到的源地址改写成网关 IP，导致命令发错地址。此时可在服务器上放一个 **host 网络的 UDP 代理**，把真实源 IP 写进数据包前缀再转发给解析程序（本方案早期部署采用过这种做法，仅是把源 IP 从网络层搬进数据层，其余逻辑完全一致）。

## 4. 与其他方案的对比

| 方案 | 问题 |
|---|---|
| 红外遥控 | 只能发不能收，拿不到空调状态，且需对准面板 |
| 拆机改电路 | 风险高，失去保修，不可逆 |
| 厂家云 API / 官方网关 | 不存在，或价格极高 |
| 更换智能面板 | 成本高，且主机与面板的通信协议未必公开 |
| **总线旁路（本方案）** | 不改动任何原设备，状态与控制双向具备，成本约一个 ESP32 + 一个总线收发模块 |

## 5. 可靠性设计小结

- **CRC 全程校验**：网关写总线前校验命令；服务器解析时校验响应
- **WiFi 断线重连**：固件内置重连逻辑，总线数据在断网期间不丢失解析规则（重连后继续）
- **服务器容错**：数据库断连自动重连并重试；非法帧/CRC 错误帧直接丢弃并记录日志
- **OTA 兜底**：设备安装后难以物理接触，保留 ArduinoOTA 网络升级能力
