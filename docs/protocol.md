# 协议

## 1. 总线协议：Modbus RTU

物理层：RS485 半双工，9600 8N1。总线上有一个主站（主机）周期性轮询各面板（每个面板一个独立从站地址，由面板工程模式设置），使用标准的 Modbus RTU 帧。一个帧由四部分组成：

```
┌────────┬──────────┬──────────────┬──────────────────────┐
│ 从站地址 │  功能码   │    数据域     │  CRC16（低字节在前）   │
│  1字节  │  1字节    │   N 字节      │       2 字节         │
└────────┴──────────┴──────────────┴──────────────────────┘
```

| 字段 | 长度 | 说明 |
|---|---|---|
| 从站地址 | 1 字节 | 目标面板的地址（工程模式设置；本方案实测为 1~7） |
| 功能码 | 1 字节 | 本总线用到两种：0x03 读保持寄存器、0x06 写单个寄存器 |
| 数据域 | N 字节 | 内容随功能码不同，见下两节 |
| CRC16 | 2 字节 | Modbus CRC-16（多项式 0xA001，初值 0xFFFF），低字节在前 |

> 帧中**没有"发送者身份"字段**，从站只校验地址和 CRC——这是本方案控制路径成立的基础。

## 2. 总线上观察到的帧

### 读请求（8 字节）

主机读取一个面板的完整状态：从地址 1 起连续读 32 个寄存器（功能码 0x03）。以查询面板 7 为例：

```
07 03 00 01 00 20 15 B4
```

| 字节 | 值 | 字段 | 含义 |
|---|---|---|---|
| 0 | 07 | 从站地址 | 面板 7 |
| 1 | 03 | 功能码 | 读保持寄存器 |
| 2~3 | 00 01 | 起始地址 | 寄存器地址 1（大端） |
| 4~5 | 00 20 | 寄存器数量 | 0x20 = 32 个 |
| 6~7 | 15 B4 | CRC16 | 低字节 0x15 在前 |

### 读响应（69 字节）

```
AA 03 40 [64 字节寄存器数据] CRCL CRCH
```

| 字节 | 值 | 字段 | 含义 |
|---|---|---|---|
| 0 | AA | 从站地址 | 与请求一致 |
| 1 | 03 | 功能码 | 读保持寄存器 |
| 2 | 40 | 字节数 | 0x40 = 64 = 32 个寄存器 × 2 字节 |
| 3~66 | … | 寄存器数据 | 32 个 16 位大端值，**寄存器地址 = 1 + 索引**（第 k 个即地址 1+k） |
| 67~68 | CRCL CRCH | CRC16 | 低字节在前 |

### 写命令（8 字节，本方案下发的控制帧）

```
AA 06 00 RR 00 VV CRCL CRCH
```

| 字节 | 字段 | 含义 |
|---|---|---|
| 0 | 从站地址 | 目标面板 |
| 1 | 功能码 | 0x06 写单个寄存器 |
| 2~3 | 寄存器地址 | 大端 |
| 4~5 | 写入值 | 大端 |
| 6~7 | CRC16 | 低字节在前 |

命令下发后不等待应答，以主机下一次轮询上报的状态为准（Web 界面约 30 秒自动刷新）。

### 网关上报的数据包

固件按收到数据的自然块原样上报，服务器只接受两种长度：

| 长度 | 内容 |
|---|---|
| 69 字节 | 一条响应帧 |
| 77 字节 | 请求帧（8 字节）+ 响应帧（69 字节）粘连 |

CRC 校验失败的帧直接丢弃，不解析、不入库。

## 3. 寄存器逆向方法

寄存器含义并非来自任何公开文档，而是**对比法**还原的：

1. 在面板上操作一个已知功能（如把温度从 24 调到 25）
2. 抓取操作前后两次响应帧，逐字节 diff
3. 变化的字节位置 → 对应的寄存器 → 该功能

对每个功能（开关机、模式、风速、水泵）重复上述过程，即得到下表。

## 4. 寄存器表

> 以下映射基于本方案的**实际设备实测确认**，不同型号/批次的空调可能不同，请用上面的对比法自行验证。

### 状态读取（响应帧 64 字节数据域）

| 寄存器地址 | 数据索引 | 含义 | 取值 |
|---|---|---|---|
| 2 | 1 | 电源 | 0=关 1=开 |
| 3 | 2 | 运行模式 | 1=冷风 2=热风 3=换气 4=地暖 5=地暖热风 |
| 4 | 3 | 设定温度 | 温度 ×10（250 = 25.0℃）|
| 5 | 4 | 风速 | 0=高 1=中 2=低 3=自动 |
| 16 | 15 | 当前温度 | 温度 ×10 |
| 23 | 22 | 水泵/地暖状态 | 非 0 = 开 |

### 控制写入（功能码 0x06，写单个寄存器）

| 寄存器地址 | 功能 | 值 |
|---|---|---|
| 2 | 电源 | 0=关 1=开 |
| 3 | 运行模式 | 1~5，同上 |
| 4 | 设定温度 | 温度 ×10 |
| 5 | 风速 | 0~3，同上 |
| 22 | 水泵控制 | 0=关 1=冷气泵 2=地暖泵 |

控制原理：**Modbus RTU 协议没有来源校验**——帧中不存在发送者身份信息，从站只判断地址是否指向自己、CRC 是否正确。且约克系统本身就有"主机向面板下发命令"的正常流程（见原理文档），面板按设计就会执行收到的写命令。因此命令帧可以直接发给面板（相当于模拟主机的写入），面板执行动作后，下一次主机轮询时正常上报新状态，控制链路与人工操作面板完全等效。

> **模式控制的注意点**：1 号面板是主控面板，其模式决定全系统模式（1 号制暖则所有面板制暖，制冷同理），主机负责把不一致的面板改回来。因此**切换模式时请写 1 号面板**；单独改其他面板的模式会被主机同步回 1 号的模式。

### 功能支持一览（能采什么、能控什么）

| 功能 | 采集（读响应帧） | 控制（写命令） | 取值 |
|---|---|---|---|
| 开关机 | ✓ 寄存器 2 | ✓ 写寄存器 2 | 0=关 1=开 |
| 运行模式 | ✓ 寄存器 3 | ✓ 写寄存器 3 | 1=冷风 2=热风 3=换气 4=地暖 5=地暖热风 |
| 设定温度 | ✓ 寄存器 4 | ✓ 写寄存器 4 | ×10，如 250 = 25.0℃ |
| 当前温度 | ✓ 寄存器 16 | —（传感器实测值，只读） | ×10 |
| 风速 | ✓ 寄存器 5 | ✓ 写寄存器 5 | 0=高 1=中 2=低 3=自动 |
| 水泵/地暖 | ✓ 寄存器 23 | ✓ 写寄存器 22 | 写：0=关 1=冷气泵 2=地暖泵 |

- **采集**（状态上报）：Web 界面显示、存库
- **控制**（命令下发）：Web 界面操作或命令行 `send_cmd.py`，命令经总线空闲窗口写入对应面板
- 以上是已逆向确认的寄存器；总线上可能还有未被逆向的其他功能

## 5. 设备 ↔ 服务器 UDP 协议

```
网关 ──── 上报 ────► :12333  svr（用 UDP 源地址识别设备）
网关 ◄─── 控制 ────  :12335  （由 websvr / svr 直发）
```

- **上报**：网关把总线数据原样打 UDP 发给服务器 12333 端口；面板身份取自 Modbus 帧中的**从站地址**，数据包的**源 IP**（即网关地址）记入 `modbusclient` 表，供下发命令寻址用
- **控制**：完整的 8 字节 Modbus 0x06 命令帧直发网关的 12335 端口；网关校验 CRC 后，等总线空闲写入
- 命令之间强制间隔 ≥5 秒

## 6. 数据库结构（PostgreSQL）

报文按"内容 + 时间"两级存储，重复的报文只存一份内容：

| 表 | 字段 | 说明 |
|---|---|---|
| `modbusmsg` | id, msg (JSONB) | 解析后的报文，完全相同的内容只存一行；`msg` 上有 hash 索引 |
| `modbustime` | id, insert_time, msg_id | 报文每次出现追加一行，即状态变化时间线 |
| `modbusclient` | device_id, ipaddr | 面板地址 → 网关 IP（从上报源地址学习），下发命令时按它寻址 |

`modbusmsg.msg` 示例（一条响应帧解析结果）：

```json
{"type": "response", "dev_address": 2, "function_code": 3,
 "byte_count": 64, "register_values": [0, 1, 1, 250, 3, ...]}
```
